# Навигатор студента: бот для MAX

[![pipeline](https://github.com/KKolyasik/max-benefits/actions/workflows/pipeline.yml/badge.svg)](https://github.com/KKolyasik/max-benefits/actions/workflows/pipeline.yml)

Чат-бот в мессенджере MAX для студентов 1–2 курса, которые переехали учиться в Петербург. Бот задаёт несколько вопросов кнопками и собирает персональную подборку льгот, стипендий и скидок: что это, как оформить, какие документы нужны и куда идти, со ссылками на официальные источники.

Это MVP 1: чат-бот, который читает карточки из базы знаний в PostgreSQL. Свежую информацию для неё ищет [агент](#агент-наполнение-базы): он находит страницы в интернете и готовит черновики карточек, а [админы](#админка-проверка-черновиков) разбирают их прямо в MAX. Одобренная карточка сразу попадает в подборки, без деплоя. Векторной БД пока нет, но место под неё заложено (см. [«Что дальше»](#что-дальше)).

## Что умеет

- **Рубрикатор**: «🎁 Льготы», «🎓 Стипендии», «🎭 Досуг и скидки», плюс «👤 Моя анкета» и «ℹ️ О боте».
- **Одно сообщение вместо ленты**: нажатая кнопка меняет своё сообщение, и меню, вопросы и подборка сменяют друг друга на одном экране, а не присылаются новыми сообщениями.
- **Анкета кнопками**, с одиночным и множественным выбором. Кнопкой «◀️ Назад» можно вернуться к предыдущему вопросу: прежний ответ будет отмечен. Вопросы общие для разделов: если вуз уже указан в «Льготах», в «Стипендиях» его не спросят.
- **Прогресс не теряется**: ответ сохраняется сразу после нажатия. Можно уйти в меню, закрыть чат или перезапустить бота, и анкета продолжится с того же вопроса.
- **Повторный заход**: если анкета раздела уже заполнена, бот предлагает «Показать подборку» или «Заполнить заново».
- **Подборка** по жёстким тегам из анкеты (вуз, форма обучения, соцстатус и т. д.). Сначала список найденного, самое важное сверху, а каждая карточка открывается отдельным экраном и листается стрелками «◀️ Назад» и «Далее ▶️». Ссылки на источники — кнопки под карточкой, и они фильтруются по вузу: студент Горного видит страницу Горного, а не ВШЭ.
- **Удаление данных**: «Моя анкета» → «Удалить мои данные».
- **Админка** для пользователей из `ADMIN_IDS`: черновики агента — карточка в том виде, как её увидят студенты, кому она покажется и источники; ✅ одобрить или ❌ отклонить. Одобренная карточка сразу видна студентам. Агента можно запустить кнопкой, а после каждого прогона приходит отчёт.
- Свободный текст не обрабатывается (по скоупу это не LLM-чат): бот мягко возвращает к кнопкам и повторяет текущий вопрос.

## Быстрый старт

### Без MAX: консольный симулятор

Токен не нужен. Удобно проверять анкету и базу знаний:

```bash
go run ./cmd/cli
```

Вводите номер кнопки, чтобы нажать её, или текст, чтобы отправить сообщение.

С базой данных симулятор показывает и админку: `-admin` даёт права админа. С `-kafka` и `-registry` он, как бот, принимает черновики и отчёты агента из Kafka, только своей группой потребителей, так что бот, запущенный рядом, тоже их получит. Кнопка «🤖 Агент» запускает агента-сервис, если он поднят (см. [«Сервис»](#сервис-расписание-и-кнопка-в-админке)). Postgres, Kafka и Schema Registry поднимаются из Compose:

```bash
docker compose up -d --wait postgres kafka schema-registry
```

```bash
go run ./cmd/cli -db 'postgres://benefits:benefits@localhost:5432/benefits?sslmode=disable' -admin -kafka localhost:9092 -registry http://localhost:8085
```

### С MAX через Docker Compose

1. Создайте бота на [business.max.ru](https://business.max.ru/) и возьмите токен в разделе «Интеграция» (токен выдают после модерации). Для разработки нужен отдельный тестовый бот: с токеном продового бот локально не запустится, потому что тот получает события через webhook (см. [«Webhook»](#webhook)).
2. Создайте `.env` и впишите в него `MAX_BOT_TOKEN`, а в `ADMIN_IDS` — ID пользователей MAX, которые будут разбирать черновики агента:
   ```bash
   cp .env.example .env
   ```
3. Запустите бота, Redis, Postgres, Kafka и Schema Registry (вместе около 1,5 ГБ памяти):
   ```bash
   docker compose up -d --build
   ```
4. В логах должно появиться `bot is running`:
   ```bash
   docker compose logs -f bot
   ```

### Локально без Docker

Без `REDIS_ADDR` сессии хранятся в памяти и пропадают при перезапуске, а без `DATABASE_URL` карточки берутся прямо из `data/knowledge.yaml` и админки нет:

```bash
MAX_BOT_TOKEN=... MAX_CA_FILE=certs/russian_trusted_root_ca.pem go run ./cmd/bot
```

```

                                     ▲                                               │        │
                                     └──────── Send / AnswerCallback ────────────────┘        │
                                                                                     ┌────────┴────────┐
                                                                            session.Store      knowledge.Base
                                                                            Redis / память     Postgres / YAML
                                                                                                     ▲
                                       агент ══Kafka══ bus ──черновики, отчёты──▶ админы в MAX ──────┘
                                             ◀══ карточки, анкета, решения, «запусти»
```

| Пакет | Что делает |
|---|---|
| [`cmd/bot`](cmd/bot/main.go) | Точка входа: конфиг из переменных окружения, сборка компонентов, graceful shutdown |
| [`cmd/cli`](cmd/cli/main.go) | Консольный симулятор диалога без MAX |
| [`internal/bot`](internal/bot/bot.go) | Стейт-машина диалога и тексты. От MAX не зависит: общается через интерфейс `Messenger` |
| [`internal/maxapi`](internal/maxapi/client.go) | Адаптер к MAX поверх [официального Go SDK](https://github.com/max-messenger/max-bot-api-client-go): webhook и long polling, отправка, ответы на кнопки, лимиты |
| [`internal/dispatch`](internal/dispatch/pool.go) | Пул воркеров: события одного пользователя строго по очереди, разных пользователей параллельно |
| [`internal/session`](internal/session/session.go) | Состояние и ответы пользователя: интерфейс `Store`, реализации Redis и in-memory |
| [`internal/knowledge`](internal/knowledge/knowledge.go) | Интерфейс базы знаний `Base`, формат карточки и её проверка, подбор по анкете (`Pick`) и реализация `Static` на YAML |
| [`internal/pgstore`](internal/pgstore/pgstore.go) | Карточки, их история и черновики в PostgreSQL; миграции при старте. Подборка читается из базы на каждый запрос |
| [`internal/moderation`](internal/moderation/moderation.go) | Черновик карточки и правила его одобрения |
| [`internal/survey`](internal/survey/survey.go) | Рубрикатор и анкета из YAML |
| [`cmd/agent`](cmd/agent/main.go) | Агент для наполнения базы: `serve` — сервис с расписанием и запуском из админки, `collect` — один прогон |
| [`internal/bus`](internal/bus/bus.go) | Связь бота с агентом через Kafka: принимает черновики и отчёты о прогонах, передаёт команду «запусти», публикует анкету, карточки и решения админов через outbox в Postgres |
| [`internal/agent`](internal/agent/collect.go) | Прогон агента, промпт, черновики и проверка. Внутри `search` (Yandex Search API, SearXNG), `fetch` (страницы и PDF), `llm` (OpenAI-совместимый API и асинхронный режим Yandex AI Studio) |
| [`internal/agent/bus`](internal/agent/bus/serve.go) | Связь агента с ботом через Kafka: читает базу из compacted-топиков, отправляет черновики и отчёты, запускает прогоны по расписанию и по командам, по одному за раз |
| [`contract`](contract/contract.go) | Контракт бота и агента: топики Kafka, сообщения, их схемы Avro и кодек для Schema Registry. Публичный пакет: агент импортирует его и из своего репозитория |

### Стейт-машина

```
menu ──раздел──▶ survey ──последний ответ──▶ подборка ──▶ menu
  │                 ▲
  └──раздел (анкета уже заполнена)──▶ confirm ──«Заполнить заново»──┘
                                        └──«Показать подборку»──▶ подборка
```

| Состояние | Что происходит |
|---|---|
| `menu` | Главное меню, ничего не в процессе |
| `survey` | Пользователь отвечает на вопросы раздела. Текущий вопрос — первый неотвеченный, поэтому продолжить можно в любой момент |
| `confirm` | Анкета раздела заполнена, бот спрашивает: показать подборку или заполнить заново |

Состояние сохраняется **до** отправки сообщений, так что сбой сети не откатывает прогресс.

Нажатая кнопка меняет своё сообщение: бот отвечает на нажатие новым экраном вместо старого, и весь диалог занимает одно сообщение. Новые сообщения бот присылает, только когда пользователь что-то написал сам: его сообщение встаёт под экраном, и ответ должен оказаться ниже. Подборка — тоже экраны: список карточек кнопками и по экрану на карточку. Ссылки карточки вынесены в кнопки: MAX показывает под изменённым сообщением превью первой ссылки из текста, и оно закрыло бы карточку. Карточка длиннее 3500 символов делится на части, которые листаются так же.

Если нажать устаревшую кнопку (второй раз, пока экран не сменился, или в старом сообщении), бот ответит «Эта кнопка уже неактуальна» и ничего не изменит, в том числе само сообщение: на нём может быть уже текущий экран. Только решения по черновикам в [админке](#админка-проверка-черновиков) остаются в чате историей: сообщение с кнопками «замораживается» с выбранным вариантом (`👉 ✅ Одобрено`), а следующий черновик приходит новыми сообщениями.

## Контент: анкета и база знаний

Оба файла можно править без программиста:

- [`data/survey.yaml`](data/survey.yaml): разделы меню и вопросы с вариантами ответов.
- [`data/knowledge.yaml`](data/knowledge.yaml): стартовые карточки подборки. Формат описан в шапке файла. При первом запуске с пустой базой бот импортирует их в Postgres, а дальше карточки меняются через [админку](#админка-проверка-черновиков). Без базы данных бот и симулятор читают карточки прямо из файла.

Карточка показывается, если ответы подходят под `match`: по **каждому** вопросу выбран **хотя бы один** из перечисленных вариантов.

```yaml
- id: social_scholarship
  categories: [benefits, scholarships]
  priority: 95
  match:
    study_form: [full_time]        # очная
    study_basis: [budget]          # и бюджет
    social_status: [orphan, disability, low_income]   # и хотя бы одно из
  title: "💳 Государственная социальная стипендия"
  summary: "..."
  steps: ["...", "..."]
  documents: ["..."]
  where: "..."
  links:
    - title: "Поддержка в Горном"
      url: "https://spmi.ru/..."
      when: {university: [mining]}  # ссылка только для студентов Горного
```

Бот проверяет оба файла при старте: опечатка в ID вопроса или варианта, ссылка не на https или условие по вопросу, которого нет в разделе, не дадут ему запуститься. `go test ./...` дополнительно перебирает около 15 тысяч комбинаций ответов и проверяет, что каждый пользователь получает хотя бы одну карточку, ни один экран подборки не выходит за лимиты MAX (длина текста, ряды и кнопки) и каждая карточка кому-то показывается.

Карточку из базы, которая после правки анкеты перестала ей соответствовать, бот не показывает и пишет о ней в лог при старте.

В Docker Compose папка `data/` примонтирована в контейнер, поэтому после правок анкеты достаточно `docker compose restart bot`, без пересборки.

> Стартовое наполнение собрано из официальных источников (сайты вузов, метрополитена, Госуслуг, Культура.РФ) в сентябре 2026 года. Правила меняются, поэтому перед показом реальным пользователям каждую карточку должен проверить человек.

## Агент: наполнение базы

Правила и суммы меняются каждый год, поэтому базу нужно обновлять. Агент делает это за человека, кроме последнего шага — проверки:

```
data/queries.yaml ─▶ поиск ─▶ страницы и PDF ─▶ модель ─▶ проверка ─▶ Kafka ─▶ бот ─▶ админы ─▶ Postgres
```

**`go run ./cmd/agent collect`** — для каждого запроса из [`data/queries.yaml`](data/queries.yaml) ищет 5 страниц (по одной с сайта) и читает их: из HTML берёт основной текст без меню (а если он подозрительно короткий — всю страницу: вузы прячут суммы и сроки в свёрнутых блоках), из PDF — текст документа, а из длинного документа — части, близкие к запросу. Запросы идут параллельно, если модель это позволяет. Модель получает тексты, анкету, карточки раздела целиком (чтобы обновлять их, а не писать заново) и список остальных карточек и отвечает JSON строго по схеме: новые карточки или обновления существующих. Код проверяет их той же функцией, что и бот при старте; с ошибками модель исправляется один раз. Ссылки берутся только из источников и текущей версии карточки, остальные агент убирает сам. Кому показывать карточку и её ссылки, решают люди: в обновлении условия остаются прежними, что бы ни ответила модель. Базу и анкету агент перед каждым прогоном берёт у бота из Kafka, какими они стали к этому моменту: так он видит карточки, одобренные после прошлого прогона, и не предлагает их заново. Черновики уходят боту тоже через Kafka, и бот сохраняет их в базу. ID черновика выводится из того, что он предлагает, поэтому то же предложение, присланное снова, для бота один черновик. Отклонённое предложение агент помнит по решениям админов и больше его не присылает. Более свежий черновик той же карточки заменяет ещё не разобранный. Kafka и реестр агент проверяет до поиска: если их нет, прогон не начнётся и ничего не потратит. Без `KAFKA_BROKERS` агент берёт базу из `data/`, а черновики пишет файлами в `drafts/`, но бот их не увидит.

Модель только читает и пересказывает: она не ищет, не ходит по ссылкам и не пишет в базу. Если по запросу нет ничего нового, модель не вызывается. Агент помнит каждую страницу отдельно: новой считается страница, которой раньше не было в выдаче, или страница с изменившимся текстом. Порядок выдачи и сайт, который на этот раз не открылся, изменением не считаются.

За прогон агент тратит не больше `LLM_TOKEN_LIMIT` токенов модели: 300 тысяч при обычных 150–200 тысячах на все запросы. Это защита от раздутого списка запросов или модели, которая слишком долго рассуждает. Запросы, на которые лимита не хватило, ждут следующего прогона: это видно в отчёте, а `collect` завершается с ошибкой.

### Сервис: расписание и кнопка в админке

**`go run ./cmd/agent serve`** — агент как сервис, так он работает на сервере. Раз в неделю, в ночь на понедельник, он запускается сам, а в админке его запускает кнопка «🤖 Агент». Чаще не нужно: суммы и тарифы меняются с 1 сентября и 1 января, а админам удобнее разбирать черновики пачкой. В сезон, с середины августа по сентябрь и в конце декабря — январе, расписание можно сделать чаще, например `AGENT_SCHEDULE=0 3 * * 1,4` — по понедельникам и четвергам. Ночью и поиск дешевле.

- Прогоны идут по одному: команда, пришедшая во время прогона, получает ответ «занят».
- Если сервис лежал, когда подошло время прогона, пропущенный прогон начнётся, как только сервис поднимется, но только один. Первый раз после установки сервис ждёт расписания или кнопки.
- О каждом прогоне агент отчитывается в Kafka: что он начался и чем кончился, сколько запросов, черновиков и токенов, а если сорвался — почему. Бот пересылает отчёты админам. Остановленный посреди прогона сервис, например при деплое, успевает сообщить, что прогон прерван.
- Что агент уже прочитал, хранится в томе `/data`, поэтому после перезапуска неизменившиеся страницы в модель не пойдут.

Локально сервис поднимается в Compose, но только по запросу, ведь прогоны стоят денег. Ключи Яндекса он берёт из `.env`, а без них ищет через SearXNG, которого тогда нужно поднять рядом:

```bash
docker compose --profile agent up -d --build agent
```

### Запуск бесплатно: SearXNG и своя модель

Поиск — локальный [SearXNG](https://github.com/searxng/searxng) (метапоиск по Google, Bing, Brave и другим, без ключей), модель — своя через [Ollama](https://ollama.com):

```bash
docker compose --profile agent up -d searxng
ollama pull qwen3:14b
```

В `.env`:

```env
LLM_BASE_URL=http://localhost:11434/v1   # или IP компьютера с Ollama в локальной сети
LLM_MODEL=qwen3:14b
```

```bash
go run ./cmd/agent collect
```

Промпт с текстами страниц занимает около 10–12 тысяч токенов, а контекст Ollama по умолчанию — 4096, и лишнее она молча обрезает. Запускайте Ollama с `OLLAMA_CONTEXT_LENGTH=32768`; с `OLLAMA_FLASH_ATTENTION=1` и `OLLAMA_KV_CACHE_TYPE=q8_0` qwen3:14b с таким контекстом помещается в 16 ГБ видеопамяти. Если контекста не хватает, агент это замечает и останавливается.

Для PDF нужен `pdftotext` из poppler (`brew install poppler`, `apt install poppler-utils`). Без него PDF читаются только по фрагментам из выдачи поиска.

### Запуск на Yandex Cloud

Поиск через Yandex Search API и модель из AI Studio работают с одним API-ключом. Создайте сервисный аккаунт с ролями `search-api.webSearch.user` и `ai.languageModels.user`, выпустите API-ключ с областями действия `yc.search-api.execute` и `yc.ai.languageModels.execute` и задайте `YANDEX_API_KEY` и `YANDEX_FOLDER_ID` (ID каталога, где лежит сервисный аккаунт; он виден в адресе консоли `console.yandex.cloud/folders/<ID>`): агент сам переключится на Яндекс.

По умолчанию модель — YandexGPT Pro 5.1 в асинхронном режиме: агент отправляет запросы в Text Generation API (`completionAsync`), а ответ забирает, когда он готов. Ждать приходится от секунд до часов, зато это вдвое дешевле. Асинхронный режим есть только у моделей Яндекса (YandexGPT, Alice AI LLM); для открытых моделей AI Studio (Qwen, gpt-oss, DeepSeek) задайте `YANDEX_ASYNC=false`, и агент пойдёт через OpenAI-совместимый Completions API, как с Ollama.

Цены на сентябрь 2026 года: поиск — 0,49 ₽ за запрос днём и 0,37 ₽ ночью, YandexGPT Pro 5.1 — 0,41 ₽ за 1000 токенов асинхронно и 0,8 ₽ синхронно. Один запрос агента — около 10 тысяч токенов, то есть ~4 ₽; полный прогон 13 запросов — около 60 ₽, а запросы с неизменившимися страницами модель не тратят. Сколько токенов ушло, агент пишет в конце прогона.

## Админка: проверка черновиков

Админы — пользователи MAX, чьи ID перечислены в `ADMIN_IDS`. Права проверяются на каждом нажатии, а не только тем, что кнопка скрыта: студент не откроет админку, даже подделав callback.

Чтобы дать админку всем на время проверки ревьюерами, поставьте в `.env` `ADMIN_FOR_ALL=true` и перезапустите бота: каждый пользователь увидит «🛠 Черновики» и «🤖 Агент», сможет одобрять и отклонять черновики и запускать агента. Отчёты агента по-прежнему получают только пользователи из `ADMIN_IDS`: списка всех пользователей у бота нет. В логе при старте будет предупреждение. После проверки уберите строку и перезапустите бота: права снова только у `ADMIN_IDS`.

- После каждого прогона агента бот присылает админам отчёт: сколько запросов, сколько черновиков прислано и ждёт проверки, сколько ушло токенов, а если прогон сорвался — почему. Кнопка «📝 Разобрать» открывает черновики. С 22 до 8 утра сообщения об агенте приходят без звука. Ещё черновики открываются кнопкой «🛠 Черновики» в меню или командой `/admin`.
- «🤖 Агент» в меню или `/agent` запускает агента: «▶️ Запустить» — обычный прогон, «🔁 Перечитать всё» — отправить модели все страницы заново, даже не изменившиеся. Бот сообщит, когда агент возьмётся за прогон, а по итогам пришлёт отчёт.
- Черновик — два сообщения. Первое — карточка в том виде, как её увидят студенты, со ссылками кнопками, и под ней источники агента: сайты со ссылками на страницы. Второе, с кнопками, — служебное: новая карточка или обновление (и что именно изменится), разделы, запрос агента, кому покажется (условие на строку, а варианты условия — каждый своей строкой) и замечания. Ссылок в нём нет намеренно: нажатая кнопка меняет своё сообщение, а MAX показывает под изменённым сообщением превью первой ссылки.
- ✅ **Одобрить**: карточка записывается в базу и в историю изменений и сразу попадает в подборки. Все проверки выполняются в той же транзакции, что и запись, поэтому черновик одобряется один раз, даже если два админа нажали одновременно, и только если он ещё подходит к базе и анкете. Если нет, кнопки «Одобрить» не будет, а бот покажет, что мешает.
- ❌ **Отклонить** или ⏭ **Пропустить**: пропущенный черновик остаётся на проверке и вернётся по кнопке «🔄 Сначала».

Каждая версия карточки хранится в таблице `card_history`: кто, когда и из какого черновика её изменил.

## Контракт: Kafka и Schema Registry

Бот и агент общаются через Kafka, а формат сообщений закреплён схемами Avro в Schema Registry. Всё, о чём они договариваются, лежит в публичном пакете [`contract`](contract/contract.go): его импортирует и агент, когда переедет в свой репозиторий. Через Kafka ходят черновики, карточки, анкета, решения админов, команды агенту и отчёты о прогонах.

Со стороны бота этим занимается [`internal/bus`](internal/bus/bus.go). При старте он создаёт топики, регистрирует схемы и публикует анкету и все карточки, а дальше раз в две секунды отправляет в Kafka outbox. Это таблица, в которую одобрение и отклонение черновика в той же транзакции пишут «карточка изменилась» и «решение принято». В Kafka уходит текущее состояние, поэтому пока Kafka недоступна, изменения просто ждут в outbox. Черновики и отчёты бот читает группой `max-benefits-bot` и подтверждает чтение черновиков только после записи в базу. Отчёты старше суток админам не пересылаются: их прочитала бы новая группа.

Со стороны агента это [`internal/agent/bus`](internal/agent/bus/serve.go). Базу он перед каждым прогоном читает из compacted-топиков от начала до текущего конца. Команды читает группой `max-benefits-agent`, а время прошлого прогона для расписания узнаёт из `agent.runs`.

| Топик | Кто → кому | Ключ | Что внутри |
|---|---|---|---|
| `knowledge.drafts` | агент → бот | ID черновика | черновик карточки (`Draft`) |
| `knowledge.cards` | бот → агент | ID карточки | актуальная база (`Card`), compacted |
| `knowledge.survey` | бот → агент | `survey` | анкета (`Survey`), compacted |
| `knowledge.decisions` | бот → агент | ID черновика | одобрено или отклонено (`Decision`), compacted: агент помнит отказы |
| `agent.commands` | бот → агент | ID команды | «запусти прогон» из админки (`RunCommand`) |
| `agent.runs` | агент → бот | ID прогона | отчёт о прогоне (`RunReport`): начался, закончился, сорвался или «занят» в ответ на команду |

- Схемы лежат в [`contract/avro`](contract/avro), по файлу на сообщение. Запись из другого файла (карточка внутри черновика) при регистрации подставляется целиком, поэтому в реестре каждая схема самодостаточна.
- Сообщение идёт в формате Confluent: нулевой байт, ID схемы в реестре и данные Avro. Его прочитает любой клиент Schema Registry, например `kafka-avro-console-consumer`.
- Схема регистрируется под полным именем записи (`maxbenefits.Draft` и т. д.) с совместимостью `FULL_TRANSITIVE`: сообщение любой версии читается любой другой. Поэтому бот и агента можно выкатывать в любом порядке, а схему можно менять только совместимо: новое поле — со значением по умолчанию, удалить — только поле со значением по умолчанию, новое значение enum — можно, старые читатели увидят `UNKNOWN`.
- Сервисы регистрируют схемы при старте. Несовместимое изменение не даст сервису запуститься, и деплой откатится.
- Топики создают сами сервисы (`contract.EnsureTopics`): одна партиция и одна реплика на единственный брокер. Автосоздание топиков в Kafka выключено.

Локально Kafka и реестр поднимаются из `docker-compose.yml`: Kafka на `localhost:9092`, реестр на `localhost:8085`.

```bash
docker compose up -d --wait kafka schema-registry
```

### Сертификат Минцифры

TLS-сертификат `platform-api2.max.ru` выдан УЦ Минцифры (Russian Trusted Root CA), которого нет в стандартных наборах сертификатов. Без него запросы падают с `x509: certificate signed by unknown authority`. Сертификат лежит в [`certs/`](certs/russian_trusted_root_ca.pem): он скачан с CDN Госуслуг (`gu-st.ru`), действует до 27.02.2032, SHA-256 `D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31`. Бот доверяет ему **только** в HTTP-клиенте MAX, в системное хранилище контейнера он не добавляется. Агент доверяет ему при чтении сайтов: многие официальные сайты (например, metro.spb.ru) тоже используют сертификаты Минцифры.

## Как закрыты требования

| Требование | Как сделано |
|---|---|
| Бот как стейт-машина | [`internal/bot`](internal/bot/bot.go): состояния `menu`, `survey`, `confirm` |
| Прогресс анкеты не теряется | Сессия пишется в Redis (AOF) после каждого ответа, до отправки сообщений |
| Модули базы знаний закрыты интерфейсом | `knowledge.Base`; бот не знает, YAML это или Qdrant |
| Работа с MAX, Docker и Docker Compose | Официальный SDK MAX, `Dockerfile`, `docker-compose.yml` (бот и Redis) |
| Использовать сохранённую анкету или перезаполнить | Состояние `confirm` и кнопка «Изменить анкету» после подборки |
| Удаление пользовательских данных | «Моя анкета» → «Удалить мои данные» |
| Поиск в базе не дольше 10 с | Сейчас это микросекунды. На каждое событие стоит таймаут 20 с с учётом пауз MAX |
| Больше 100 клиентов в пике | Пул воркеров с шардированием по `user_id`. Нагрузочный тест: 300 пользователей проходят анкету одновременно, самый медленный шаг занимает меньше 0,1 с при сетевой задержке 20 мс |

Лимиты MAX API тоже учтены: не больше 30 запросов в секунду на бота (держим 25), 2 сообщения в секунду в один диалог (пауза 500 мс), до 4000 символов в сообщении (подборка показывается по карточке на экран, а длинная карточка делится на части по 3500), до 30 рядов кнопок (в списке подборки не больше 25 карточек, остальные листаются). Нажатие кнопки — один запрос к MAX: экран меняется в том же ответе на нажатие. Ответ `429 Too Many Requests` повторяется автоматически. На пиковую нагрузку главное ограничение даёт сам лимит MAX в 30 запросов в секунду: 100 человек, нажавших кнопку в одну секунду, получат ответ в течение нескольких секунд.

## CI/CD и деплой

Всё описано в [`.github/workflows/pipeline.yml`](.github/workflows/pipeline.yml): один пайплайн на пул-реквест в `main`, на пуш в `main` и на ручной запуск (**Actions → pipeline → Run workflow**, на любой ветке или теге).

```
lint ─┐
      ├─▶ build ─▶ deploy (ждёт подтверждения)
test ─┘
```

| Джоба | Что делает |
|---|---|
| `lint` | `golangci-lint` по [`.golangci.yml`](.golangci.yml) (стандартный набор плюс errorlint, gocritic, unparam и др., форматирование gofmt/goimports), `hadolint` для Dockerfile бота и агента и `actionlint` для самого пайплайна |
| `test` | `go test -race` с покрытием. Тесты хранилища идут на настоящем Postgres из `services`, `coverage.out` сохраняется в артефактах |
| `build` | Образы бота и агента `linux/amd64` с тегом — полным sha коммита. В Docker Hub пушится всё, кроме пул-реквестов: их образы только собираются. Образ агента называется по образу бота: `IMAGE` без `-bot` и с `-agent`, например `kkolyasik/max-benefits-agent` |
| `deploy` | Выкатка на сервер. Джоба работает в окружении `production`, которое требует подтверждения, поэтому ждёт кнопку, как manual-джоба в GitLab. В пул-реквестах её нет |

**Выкатить:** в запуске пайплайна у джобы `deploy` нажмите **Review deployments → Approve and deploy**. Выкатывается образ, собранный этим же запуском, без пересборки. Неподтверждённый деплой ничему не мешает: запуск просто ждёт, а через 30 дней GitHub его закрывает.

**Откатиться или выкатить другую версию:**
- в течение 30 дней — откройте старый запуск и перезапустите у него джобу `deploy` (**Re-run jobs**): образ того коммита уже лежит в Docker Hub;
- любую версию — поставьте на коммит git-тег и запустите пайплайн вручную на этом теге. Он соберёт образ и тоже спросит подтверждения:

  ```bash
  git tag v1.0.0 <коммит> && git push origin v1.0.0
  ```

Как устроена выкатка:
1. `appleboy/scp-action` кладёт [`deploy/docker-compose.prod.yml`](deploy/docker-compose.prod.yml) в `DEPLOY_PATH` на сервере.
2. `appleboy/ssh-action` проверяет, что в `.env` на сервере есть токен бота и ключ Яндекса для агента, скачивает оба образа (если какого-то нет, деплой падает, ничего не трогая) и записывает в `.env` их теги и `WEBHOOK_URL`. Остальные строки он не трогает, а при первом деплое добавляет случайные `POSTGRES_PASSWORD` и `WEBHOOK_SECRET`. Потом перезапускает бота и агента и ждёт в логах `bot is running` и `agent is running`. Если за минуту кто-то из них не стартовал, возвращается предыдущий `.env`, а с ним прежние образы, и деплой падает.

Анкета лежит внутри образа, поэтому откат возвращает её вместе с кодом. Карточки живут в Postgres: образ только заполняет пустую базу, а одобренное админами переживает и деплой, и откат. Какая версия сейчас на сервере, из какой ветки и когда выкачена, записано в `VERSION` рядом с `.env`.

Логи запусков публичного репозитория видны всем, поэтому пайплайн не печатает ни секретов, ни содержимого `.env`.

### Настройка репозитория

Один раз, в **Settings** репозитория на GitHub:

1. **Environments → New environment** `production` → **Required reviewers**: добавьте тех, кто может выкатывать. Без ревьюера деплой пойдёт сразу, без кнопки. В **Deployment branches and tags** можно разрешить только `main` и теги `v*`.
2. **Secrets and variables → Actions → Secrets → New repository secret**. Все настройки — секреты: логи Actions публичного репозитория видны всем, а секреты в них маскируются. Кладите их в секреты репозитория, не окружения: часть из них читает джоба `build`. Посмотреть сохранённый секрет нельзя, только перезаписать, так что держите значения у себя.

   | Секрет | Пример | Что это |
   |---|---|---|
   | `DOCKERHUB_USERNAME` | `kkolyasik` | Логин Docker Hub |
   | `DOCKERHUB_TOKEN` | — | Access token Docker Hub с правами Read & Write (hub.docker.com → Account settings → Personal access tokens) |
   | `IMAGE` | `kkolyasik/max-benefits-bot` | Репозиторий образа в Docker Hub |
   | `DEPLOY_HOST` | IP сервера | Куда выкатывать. Пока секрет не задан, джобы `deploy` в пайплайне нет |
   | `DEPLOY_USER` | `maxbot` | Пользователь на сервере |
   | `DEPLOY_SSH_KEY` | — | Приватный SSH-ключ пользователя `DEPLOY_USER`, целиком, со строками `BEGIN`/`END` |
   | `DEPLOY_HOST_FINGERPRINT` | `SHA256:…` | Отпечаток ECDSA-ключа сервера, защищает от подмены сервера: `ssh-keyscan -t ecdsa <сервер> \| ssh-keygen -lf -` |
   | `WEBHOOK_URL` | `https://<домен>/webhook` | Адрес, на который MAX присылает события |
   | `DEPLOY_PATH` | `/opt/max-benefits` | Необязательный: папка приложения на сервере, по умолчанию `/opt/max-benefits` |

### Токен бота

Токен лежит только на сервере, в `/opt/max-benefits/.env` (строка `MAX_BOT_TOKEN=...`), и деплой его не меняет. Чтобы сменить токен, поправьте эту строку и перезапустите бота:

```bash
sudo -u maxbot docker compose -p max-benefits -f /opt/max-benefits/docker-compose.prod.yml up -d --force-recreate bot
```

Если сделаете репозитории образов в Docker Hub приватными, один раз залогиньтесь на сервере от имени `maxbot` (`sudo -u maxbot docker login`).

### Ключ Яндекса для агента

Агенту на сервере нужны `YANDEX_API_KEY` и `YANDEX_FOLDER_ID` (как их получить, см. [«Запуск на Yandex Cloud»](#запуск-на-yandex-cloud)). Они, как и токен бота, лежат только в `/opt/max-benefits/.env`, и без них деплой не начнётся. В контейнер агента из `.env` попадают только его настройки: ключ, каталог, `AGENT_SCHEDULE`, `LLM_MODEL`, `LLM_TOKEN_LIMIT`, `YANDEX_ASYNC` и `LOG_LEVEL`. Токен бота агент не видит. Сменить ключ или расписание — поправить строку и перезапустить агента:

```bash
sudo -u maxbot docker compose -p max-benefits -f /opt/max-benefits/docker-compose.prod.yml up -d agent
```

### Сервер

Бот работает на сервере `DEPLOY_HOST` под отдельным пользователем `maxbot` (`DEPLOY_USER`): он входит в группу `docker`, sudo у него нет, а его ключ открыт с опцией `restrict` (без проброса портов и агента). Всё приложение лежит в `/opt/max-benefits` (`DEPLOY_PATH`). Снаружи бот доступен только через nginx: его порт `8080` опубликован на хосте как `127.0.0.1:8081` (`8080` на хосте занят другим проектом; другой порт задаётся строкой `BOT_PORT=` в `.env`). Redis, Postgres, Kafka, Schema Registry и агент доступны только внутри сети проекта. Kafka с реестром занимают около 1 ГБ памяти, а топики создают сами сервисы при старте.

Пароль Postgres деплой один раз генерирует в `/opt/max-benefits/.env` (`POSTGRES_PASSWORD`). Админов нужно вписать туда же вручную и перезапустить бота, пересборка не нужна:

```bash
echo 'ADMIN_IDS=<ID в MAX>' | sudo -u maxbot tee -a /opt/max-benefits/.env
```

```bash
sudo -u maxbot docker compose -p max-benefits -f /opt/max-benefits/docker-compose.prod.yml up -d bot
```

Карточки теперь живут только в базе, поэтому нужен бэкап. Например, ежедневный дамп по cron пользователя `maxbot`:

```
0 4 * * * mkdir -p /opt/max-benefits/backups && docker compose -p max-benefits -f /opt/max-benefits/docker-compose.prod.yml exec -T postgres pg_dump -U benefits benefits | gzip > /opt/max-benefits/backups/benefits-$(date +\%F).sql.gz
```

Полезные команды на сервере:

```bash
sudo -u maxbot docker compose -p max-benefits -f /opt/max-benefits/docker-compose.prod.yml logs -f bot
```

```bash
sudo -u maxbot docker compose -p max-benefits -f /opt/max-benefits/docker-compose.prod.yml logs -f agent
```

```bash
sudo cat /opt/max-benefits/VERSION
```

С одним токеном бот должен работать ровно в одном месте. Поэтому при старте в режиме webhook бот удаляет другие вебхуки своего токена, а в режиме long polling отказывается запускаться, пока вебхук есть.

### Webhook

На проде MAX сам присылает события на `WEBHOOK_URL` — `https://<домен>/webhook`. Long polling документация MAX для продакшена не рекомендует: он ограничен по скорости и по сроку хранения событий. Локально бот по-прежнему работает через long polling: для webhook нужен публичный https-адрес.

```
MAX ──https──▶ nginx на хосте (TLS, Let's Encrypt) ──▶ 127.0.0.1:8081 ──▶ бот в Docker (:8080)
```

- При каждом старте бот поднимает HTTP-сервер и только потом подписывается на `WEBHOOK_URL` с секретом из `.env`. Повторная подписка на тот же адрес безопасна.
- MAX принимает только https на порту 443 с сертификатом доверенного УЦ (или УЦ Минцифры). Самоподписанный не подойдёт.
- Бот отвечает 200, как только событие встало в очередь. Во время остановки он отвечает 503, и MAX повторит доставку: первый повтор через минуту, дальше реже, всего до 8 часов. Поэтому подписка при остановке не удаляется, и события за время перезапуска не теряются. Если за 8 часов MAX так и не получит успешного ответа, он сам отпишет бота. Следующий старт бота подпишет его заново.

nginx и сертификат настраиваются на сервере один раз, вручную (деплой делает `maxbot`, у которого нет sudo). Конфиг лежит в `/etc/nginx/sites-available/<домен>`:

```nginx
server {
    listen 80;
    server_name <домен>;

    location = /webhook {
        limit_except POST { deny all; }
        proxy_pass http://127.0.0.1:8081;
        proxy_set_header Host      $host;
        proxy_set_header X-Real-IP $remote_addr;
        client_max_body_size 1m;
    }

    location / {
        return 404;
    }
}
```

Сертификат выпускает и продлевает certbot. Он же добавляет в этот конфиг `listen 443 ssl` и редирект с http:

```bash
sudo certbot --nginx -d <домен>
```

Проверить снаружи, что цепочка работает (без секрета бот должен ответить 401):

```bash
curl -i -X POST https://<домен>/webhook
```

## Что дальше
